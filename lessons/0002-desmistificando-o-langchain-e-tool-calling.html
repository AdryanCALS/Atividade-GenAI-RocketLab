Desmistificando o LangChain e a Mecânica de Tool Calling

Como o framework coordena mensagens, ferramentas em Python e o modelo de linguagem sem magia negra

1. O que é o LangChain (e o que ele NÃO é)?

Para entender o LangChain, precisamos começar com uma verdade libertadora: modelos de linguagem (LLMs) são apenas preditores probabilísticos de texto.

O modelo openai/gpt-oss-120b que estamos usando via Groq não tem acesso à internet, não tem acesso ao seu disco rígido, não sabe abrir um arquivo .db e não possui memória entre uma requisição e outra. Ele é uma função pura: recebe uma lista de textos e gera o próximo texto mais provável.

O LangChain é o "sistema nervoso" que envelopa essa LLM. Ele não substitui o modelo; ele fornece a infraestrutura de engenharia de software para:

  • Gerenciar o ciclo de conversação: Traduzir perguntas e respostas em uma estrutura formal de mensagens padronizadas.
  • Inspecionar suas funções Python: Ler seus tipos (type hints) e documentação (docstrings) e traduzi-los em esquemas que a LLM entende.
  • Fechar o loop de execução (ReAct): Quando a LLM pede para rodar uma consulta, o LangChain chama sua função local, recolhe a saída e entrega de volta ao modelo.

2. A Ilusão do Tool Calling: A LLM NUNCA executa Python!

Um dos maiores equívocos de quem começa na área é acreditar que a LLM executa a ferramenta dentro dela. Isso nunca acontece. Veja o aperto de mãos exato do Tool Calling: 

[Você] "Qual o filme mais lucrativo?"
  │
  ▼
[LangChain] Monta a lista com [HumanMessage] e as ferramentas disponíveis
  │
  ▼
[Groq / gpt-oss-120b] 
  Recebe o pedido e percebe: "Não sei responder de cabeça, preciso de SQL!"
  Gera uma resposta especial: AIMessage com tool_calls:
  [{'name': 'execute_sql', 'args': {'query': 'SELECT ...'}}]
  │
  ▼
[LangChain / Seu Código Python]
  1. Intercepta o pedido da LLM
  2. Executa a SUA função Python localmente na SUA máquina
  3. Seus Guardrails validam a query
  4. Seu SQLite roda o SELECT com segurança
  5. Empacota os dados retornados em um ToolMessage
  │
  ▼
[Groq / gpt-oss-120b]
  Recebe o histórico completo + o ToolMessage com os dados reais
  Lê os números e sintetiza a resposta final em português humano
  │
  ▼
[Você] Recebe: "O filme mais lucrativo do catálogo é Avatar: O Caminho da Água..."

3. As 4 Peças Fundamentais do LangChain que Usaremos

1. ChatGroq (`langchain_groq`)

É a ponte entre o LangChain e a infraestrutura de alta velocidade da Groq. É nele que configuramos o modelo openai/gpt-oss-120b e a temperatura (usamos 0 para respostas analíticas e determinísticas).

2. O Decorador `@tool` (`langchain_core.tools`)

É um decorador mágico que transforma qualquer função Python normal em uma ferramenta do agente. O ponto mais crítico aqui é a Docstring: 

from langchain_core.tools import tool

@tool
def inspect_tables(table_names: list[str]) -> str:
    """Retorna o esquema (colunas e tipos) das tabelas solicitadas.
    
    Args:
        table_names: Lista com os nomes exatos das tabelas a serem inspecionadas.
    """
    # Seu código Python de consulta ao sqlite_master
    return "..."
Por que a Docstring é Vital?

A LLM nunca vê o código interno da sua função. Ela lê exclusivamente o nome da função, os parâmetros e a docstring. A docstring funciona literalmente como o System Prompt da ferramenta!

3. `llm.bind_tools([tool1, tool2])`

Informa ao modelo: "Aqui estão as funções que você tem autorização para solicitar quando precisar de dados externos." O modelo passa a gerar respostas com o campo tool_calls preenchido quando achar necessário.

4. O Quarteto de Mensagens (`langchain_core.messages`)

  • SystemMessage: A bússola moral e técnica do agente (regras e persona).
  • HumanMessage: A pergunta que você faz ao agente.
  • AIMessage: O que o modelo devolve (pode ser o texto final ou um pedido de tool).
  • ToolMessage: O resultado produzido pela sua máquina, indexado pelo tool_call_id.
